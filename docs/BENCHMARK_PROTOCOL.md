# NameBridge — benchmark protocol (phase 0, week 2)

Draft, 26 Oct 2026. Fixed **before** any data is generated or any model is run (`CONCEPT-IDEA.md` §9.3), so that results can't steer the rules. Changes after week 6 need a dated note in `RESEARCH_LOG.md`, and both versions are reported. Sources are listed at the end ([B1]–[B9]).

## 1. What is being tested

How well each option finds the right person or relative among records with differently written names, in the Great Lakes → Malawi corridor, **on synthetic data**.

The options are:

- **Option 5:** deterministic and phonetic rules.
- **Option 2:** Splink alone.
- **Option 3:** graph expansion alone.
- **Option 1:** the hybrid.
- **Option 4:** a commercial tool, only if a free licence exists and no data leaves our machine.

Every result is labelled **preliminary (synthetic only)**. A decisive benchmark needs real error patterns (§9.1), which require a partner.

## 2. The synthetic world

### 2.1 People and families

- **Size (v0.1):** about **3,000 invented people in about 1,000 families**, observed in about **10,000 records**. That is roughly 3 records per person, spread unevenly across sources. Size is not the point; coverage of the error types is.
- **Origin mix** follows Dzaleka: about 65% DRC, 22% Burundi, 12% Rwanda (`SCOPE.md` §1). Each origin is large enough to report on its own; if needed, the smaller groups are oversampled and the weights recorded.
- **Ages** include many children, because women and children are 93% of Dzaleka's population (situation research). At least 30% of people are under 18 at the record date. These records carry the protected-person flag (C7).

### 2.2 Names: generated by naming system, from sourced rules

| Origin | Generation rule | Source |
| --- | --- | --- |
| **Rwanda** | Kinyarwanda surname chosen per child, plus a given name (often Christian). A child may share one element with a parent, but never all of them. Written surname-first, often in capitals, in local records | Law 71/2024 arts 38–39 [B1]; HRW 1999 [B2]; [B3] |
| **Burundi** | Kirundi name plus prénom(s), freely chosen. With probability *p*, a son receives his father's name (patronymic practice). *p* is a **varied parameter**, because the evidence is disputed | Code des personnes et de la famille, art. 13 [B4]; Univ. of Burundi / Bigangara [B5] |
| **DRC** | Prénom + nom + postnom; order and spelling fixed in civil records. If a parent passes their nom on, at least one different element is added. Same-family members with the same nom carry different complementary elements. A married woman keeps her name and may add her husband's | Family Code arts 56–62 [B6] |
| **Token frequencies** | DRC: aggregate token frequencies from CongoNames (counts under 5 suppressed; DR-1). Rwanda and Burundi: curated token lists from the packs (week 4), with frequencies marked `estimated` | [B7]; packs |

### 2.3 Record sources and error types

Each person is observed through simulated **sources**. Each source has its own fields and error profile:

- registration form (written, French or English labels);
- oral tracing request (via an interpreter);
- camp distribution list;
- school list;
- passport MRZ (rare).

Errors are injected **GeCo-style** [B8], with documented rates per source:

| Error type | Example (invented names) |
| --- | --- |
| Name order changed | `NIYONZIMA Eric` ↔ `Eric Niyonzima` |
| Kinyarwanda or Kirundi spelling variants (official orthography often not followed [B2]) | `Uwimana` / `Uwimanna` |
| Christian-name variants across French, English and Swahili | `Jean` / `John` / `Yohana` |
| Postnom dropped, or nom and postnom swapped | `Mutombo Kalala Pierre` → `Pierre Mutombo` |
| Married name added | (DRC art. 62) |
| Phonetic errors from oral reports and interpreters | `l`/`r` confusion in Kinyarwanda and Kirundi |
| Typos and OCR errors | `rn`→`m`, `1`→`l` |
| Truncation and missing diacritics | MRZ and ASCII fields |
| Incomplete or rounded ages; age heaping | "about 10" |
| Places renamed over time | Burundi provinces 2025; DRC provinces 2015 |
| **Hard negatives** | Different people with common names, same age band, same area |
| **Adversarial pairs** | Different families built to look alike |

### 2.4 Gold labels

- **Same-person** clusters.
- **Family relationships**: parent, sibling, spouse, household.
- **Non-match** pairs, including all hard negatives.
- The "expected" outcome for each query: found / not present / insufficient evidence. Some sought people have **no** record, so abstention can be tested.

## 3. Splits (§9.3)

- **Train / dev / test = 60 / 20 / 20, split by family.** Every member of a family, and every record of a person, falls in the same split, so the same identity can't leak across splits [B9].
- **Temporal holdout:** a further set of records "dated" after a cutoff, with newer patterns: renamed provinces, new arrivals, more passport records. It is used only once, at the end.
- **The test set is frozen** once generated, with its seed. No tuning on test or holdout. Thresholds are chosen on dev.

## 4. Two tracks

1. **Name-only search:** the query is a name, possibly with a parent's name. This measures what the name graph contributes.
2. **Full-evidence resolution:** names plus age, place, relatives and event. This measures the whole system. §9.3 requires the two to be reported separately.

## 5. Metrics (§9.2)

| Metric | Measured at | Note |
| --- | --- | --- |
| **Recall@K** (K = 1, 5, 10, 20) | Retrieval | Share of queries whose true person or relative appears in the top K |
| Pairwise **precision, recall, F1** | Each threshold | Plus the precision–recall curve |
| **Cluster quality** | After clustering | Entity-centric measures, because pairwise P/R can mislead for groups [B9] |
| **False-match rate** | Review and confirmation thresholds | Reported per slice |
| **False-non-match rate** | All thresholds | Per language, script, origin and source |
| **Calibration** | Scores | Reliability diagram and expected calibration error. A score of 0.8 should match about 80% observed |
| **Abstention** | Queries whose person isn't present | Share correctly answered "not found" or "insufficient evidence" |
| **Reviewer load** (proxy) | Review queue | Candidates per query above the review threshold |
| **Sensitive fields requested** (proxy) | Progressive disclosure | Fields opened per resolved synthetic case (week 9) |
| **Explanation coverage** | Every surfaced candidate | Share with a complete, valid path (observation → transforms → graph edges → weights) |

**Uncertainty:** 95% intervals by bootstrap **over families**, not over pairs.

## 6. Fairness slices

Every metric is reported for each of these slices, never only as a global average (§9.3):

- **origin / pack:** RW, BI, CD;
- **source type;**
- **record completeness:** number of non-empty fields;
- **age group:** child or adult;
- **sex:** synthetic, so lawful to measure;
- **error type** (from §2.3);
- **name frequency:** rare vs common tokens.

**Gap flag:** a slice's false-non-match rate more than **1.5×** the best slice's at the same threshold is flagged in the report and discussed.

## 7. Cost of errors and thresholds

The cost of each kind of error depends on the step (decided 26 Oct 2026; to confirm with the professor):

| Step | Worse error | Proposed ratio | How the threshold is set (on dev) |
| --- | --- | --- | --- |
| **Retrieval** (who enters the candidate list) | **Missed candidate** (the person is never seen by a human) | Missed : false = **10 : 1** | Highest threshold that keeps **recall@20 ≥ 0.95** |
| **Review priority** (order of the queue) | Balanced | 1 : 1 | Maximise F1; report the queue length |
| **Confirmation** (a reviewer may treat the pair as the same person) | **False match** (wrong person told, wrong child released, location exposed) | False : missed = **10 : 1** overall; **100 : 1 for minors** | Lowest threshold with **precision ≥ 0.99** (adults) and **≥ 0.999** (minors) on dev; abstain below it |

**Notes:**

- These targets are set **before** any results. If they turn out to be unreachable on synthetic data, the report says so; we don't lower the bar quietly.
- **A name-only score never reaches the confirmation step,** whatever its value (§5.6).
- Confirmation is still a **human decision**. The threshold only decides what the reviewer is shown as "strong evidence".

## 8. Procedure

1. **Week 6:** write the generator (seeded, versioned). Generate train, dev, test and holdout. Freeze test and holdout. Commit the generator and seeds; keep the generated data reproducible.
2. **Weeks 7–8:** fit and tune each option on train and dev only.
3. **Week 8:** run each option once on test. Report every metric × slice × track.
4. **Week 9:** run the temporal holdout once. Write the report, including failures, unreachable targets and differences from the §6 design scores.

## 9. Limits

- **The data is synthetic.** Results show whether the methods handle the error types we know about, not the ones we don't. The decisive benchmark needs real, governed error patterns (§9.1) and a partner.
- **Kinyarwanda and Kirundi token frequencies are estimates** until a sourced frequency list exists.
- **The Burundi rule is disputed** (`SCOPE.md` §1), so results are reported across the range of *p*.
