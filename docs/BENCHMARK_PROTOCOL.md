# NameBridge — benchmark protocol (phase 0, week 2)

Draft, 26 Oct 2026. Fixed **before** any data is generated or any model is run (`CONCEPT-IDEA.md` §9.3), so that results can't steer the rules. Changes after week 6 need a dated note in `RESEARCH_LOG.md`, and both versions are reported. Sources are listed at the end ([B1]–[B9]).

## 1. What is being tested

How well each option finds the right person or relative among records with differently written names, in the Great Lakes → Malawi corridor, **on synthetic data**.

The options are:

- **Option 5:** deterministic and phonetic rules.
- **CPIMS+-style baseline:** what caseworkers actually use today. It is reimplemented from Primero's open source [B10]: name tokens encoded with Double Metaphone, a boosted full-text match over the same fields, scores divided by the best score in the list, and the labels "likely" and "possible". Ethnicity fields are left out, so the baseline runs without them (C12).
- **Option 2:** Splink alone.
- **Option 3:** graph expansion alone.
- **Option 1:** the hybrid.
- **Option 4:** a commercial tool, only if a free licence exists and no data leaves our machine.

Every result is labelled **preliminary (synthetic only)**. A decisive benchmark needs real error patterns (§9.1), which require a partner.

## 2. The synthetic world

### 2.1 People and families

- **Size (v0.1): about 26,000 invented people in about 8,700 families**, observed in about **78,000 records** (about 3 per person, spread unevenly across sources).
  - The size is **derived from the targets in §7, not chosen**. `namebridge/src/namebridge/benchmark/sample_size.py` computes the minimum: **25,300**, rounded up.
  - The binding constraint is the minors' confirmation precision (≥ 0.999). Even with one false match, the 95% bound needs 4,742 true pairs of minors in the test set. That is multiplied by a design effect of 1.6, because records cluster in families.
  - The six key slices (3 origins × child or adult) each need about 1,471 pairs to detect a 1.5× gap in missed matches.
  - Decided by the user on 26 Oct 2026, replacing an earlier 3,000 that Claude had chosen without a derivation.
- **Origin mix: equal thirds** (DRC, Burundi, Rwanda), so every origin reaches its slice minimum. Results are also reported **re-weighted** to Dzaleka's real mix (about 65 / 22 / 12%, `SCOPE.md` §1), with the weights recorded.
- **Ages: about half under 18** at the record date, so the minors' slice reaches its minimum. Women and children are 93% of Dzaleka's population (situation research). These records carry the protected-person flag (C7).

### 2.2 Names: generated by naming system, from sourced rules

| Origin | Generation rule | Source |
| --- | --- | --- |
| **Rwanda** | Kinyarwanda surname chosen per child, plus a given name (often Christian). A child may share one element with a parent, but never all of them; sharing a father's element happens with probability *q*, a **varied parameter** because accounts conflict. Gender-marked prefixes are kept consistent with the generated sex (e.g. `Nyira-`, `Muka-` feminine; `Nya-`, `Munya-`, `Rwa-` masculine) [B17]. They are used only for generation, never to infer anyone's sex (C12). Written surname-first, often in capitals, in local records | Law 71/2024 arts 38–39 [B1]; HRW 1999 [B2]; [B3] |
| **Burundi** | Kirundi name given first, with a French Christian prénom added later; the Kirundi name then works as the surname [B18]. Both are freely chosen. With probability *p*, a son receives his father's name (patronymic practice). *p* is a **varied parameter**, because the evidence is disputed | Code des personnes et de la famille, art. 13 [B4]; Univ. of Burundi / Bigangara [B5] |
| **DRC** | Prénom + nom + postnom; order and spelling fixed in civil records. If a parent passes their nom on, at least one different element is added. Same-family members with the same nom carry different complementary elements. A married woman keeps her name and may add her husband's | Family Code arts 56–62 [B6] |
| **Name elements** | Drawn from the **naming profiles** (§2.4): common elements in proportion to their real frequency; rare elements replaced by **invented** ones built from the profile's patterns | §2.5 |

### 2.3 Record sources and error types

Each person is observed through simulated **sources**. Each source has its own fields and error profile:

- registration form (written, French or English labels);
- oral tracing request (via an interpreter);
- camp distribution list;
- school list;
- passport MRZ (rare).

Errors are injected **GeCo-style** [B8], with documented rates per source:

| Error type | Example (invented names) |
| --- | --- |
| Name order changed | `NIYONZIMA Eric` ↔ `Eric Niyonzima` |
| Kinyarwanda or Kirundi spelling variants (official orthography often not followed [B2]) | `Uwimana` / `Uwimanna` |
| Christian-name variants across French, English and Swahili | `Jean` / `John` / `Yohana` |
| Postnom dropped, or nom and postnom swapped | `Mutombo Kalala Pierre` → `Pierre Mutombo` |
| Married name added | (DRC art. 62) |
| Phonetic errors from oral reports and interpreters | `l`/`r` confusion in Kinyarwanda and Kirundi |
| Typos and OCR errors | `rn`→`m`, `1`→`l` |
| Truncation and missing diacritics | MRZ and ASCII fields |
| Incomplete or rounded ages; age heaping | "about 10" |
| Places renamed over time | Burundi provinces 2025; DRC provinces 2015 |
| **Child's report:** young children give only first names or nicknames, or confuse relationships ("brother" for "father") [B10] | A tracing request recording only "Papa Jean" |
| **Adopted name in exile** (ordered, `NAME_CHANGE.md`): **step 1**, the Christian given name is replaced (often by a Muslim/Swahili name) and the surname kept, with probability *s1*; **step 2**, the surname is also replaced, with probability *s2* < *s1*. Both are varied parameters, and higher for records made outside the camp. A false claimed nationality is added at a low, varied rate [B18] | Step 1: the right outcome is a **"possible name change"** candidate, found through the surname plus non-name evidence and routed as protected. Step 2: abstain unless non-name evidence is strong; never confirm |
| **Hard negatives** | Different people with common names, same age band, same area |
| **Adversarial pairs** | Different families built to look alike |

### 2.4 How reality enters: patterns with sources, never people

The synthetic world must behave like reality, or the dictionary will learn the wrong things. **Reality enters as patterns with sources, never as people.** Every generator parameter carries a source and a confidence level, like a graph edge (§5.1A).

| Layer | What it gives | Sources |
| --- | --- | --- |
| 1. Real names | Which name elements exist and how common they are | DRC: CongoNames [B7]. Rwanda: national exam result lists published by NESA [B11]. Burundi: **gap**, to find in week 4 |
| 2. Real structure | Element order, number of names, who may share what | Laws and onomastic studies [B1]–[B6] |
| 3. Real variation | How the same name changes | UN Security Council 1533 (DRC) sanctions list aliases [B12], e.g. `KAKOLELE`/`KAKORERE` (l/r), `MPAMO`/`MPANO`, `LUMISA`/`LUMINSA`/`LUMWINSA`. The Kinyarwanda spelling reform of 13 Oct 2014, where old and new forms coexist [B13]. Phonology: prenasalised consonants, digraphs, vowel length [B13] |
| 4. Real error rates | How often names come out wrong, and for whom | About 22% of name values differ between linked records of the same person, and 14% of dates of birth; algorithms "developed on anglicised names" fail on local names (South Africa) [B14]. `Semaganda`/`Ssemaganda`, 2 vs 3 names (Uganda) [B15]. Errors are more frequent when the name is unfamiliar to whoever records it [B16]: the generator raises the error rate when the recorder's language differs from the name's |
| 5. Real demography | Origin, age, family and separation scenarios | Dzaleka figures (`SCOPE.md` §1); HDX place names; published tracing cases (USCRI, Red Cross) turned into scenario templates, never individuals |

#### Naming profiles: study the data, keep the findings, delete the data

Real name lists (class R, `DATA_RULES.md` DR-1) are used **only to build a naming profile per origin**. The raw lists are then deleted. A profile holds:

- **Structure:** distribution of the number of elements, and their positions (prénom / nom / postnom; surname-first).
- **Element frequencies** by position, sex, province and year. Only elements seen **5 or more times**.
- **Patterns inside names:** character n-grams, prefixes and endings (e.g. `Ka-`, `Mu-`, `-imana`). Used to **invent** new, plausible elements for rare-name slots.
- **Trends over time** (e.g. 2008 vs 2023). These feed the temporal holdout.
- **Variant pairs** found inside the corpus (similar elements, both frequent). These enter the graph as `proposed` edges with a `statistical` confidence basis, after review.
- **Never:** any pattern linking names to ethnicity, clan, tribe or religion (C12; `THREAT_MODEL.md` T8). Province, language and time are enough.

#### Generation by recombination

The generator never copies a real full name. It **recombines** common elements following the profile's probabilities (e.g. which prénoms go with which noms, by province and period), and fills rare-name slots with **invented** elements. The patterns survive; the person does not.

#### Realism checks (before the test set is frozen, week 6)

1. **Fidelity test** (local; only numbers leave the machine): synthetic vs profile on structure, length, character n-grams, element frequency and province distribution. The measure is Jensen–Shannon divergence, with a limit fixed before the comparison; if it is exceeded, the generator is corrected.
2. **Copy test:** the share of synthetic full names that coincide with a real full name. It is computed once, while the raw list still exists. Only the percentage is kept, never the names. Some coincidence is normal for common names; a high share means the generator is copying.
3. **Real-pattern test set:** the attested variants from layer 3 (sanctions-list aliases, 2014 spelling forms) are kept outside the repo as class R. They give a small **real** measure of name-only search (track 1): does the graph link `Kakolele` to `Kakorere`?
4. **Sensitivity analysis:** the true error rate in Dzaleka's records is unknown, so results are reported across a range of name-error rates (e.g. 10%, 22%, 35%), not at one value.

### 2.5 Gold labels

- **Same-person** clusters.
- **Family relationships**: parent, sibling, spouse, household.
- **Non-match** pairs, including all hard negatives.
- The "expected" outcome for each query: found / not present / insufficient evidence. Some sought people have **no** record, so abstention can be tested.

## 3. Splits (§9.3)

- **Train / dev / test = 60 / 20 / 20, split by family.** Every member of a family, and every record of a person, falls in the same split, so the same identity can't leak across splits [B9].
- **Temporal holdout:** a further set of records "dated" after a cutoff, with newer patterns: renamed provinces, new arrivals, more passport records. It is used only once, at the end.
- **The test set is frozen** once generated, with its seed. No tuning on test or holdout. Thresholds are chosen on dev.

## 4. Two tracks

1. **Name-only search:** the query is a name, possibly with a parent's name. This measures what the name graph contributes.
2. **Full-evidence resolution:** names plus age, place, relatives and event. This measures the whole system. §9.3 requires the two to be reported separately.

## 5. Metrics (§9.2)

| Metric | Measured at | Note |
| --- | --- | --- |
| **Recall@K** (K = 1, 5, 10, 20) | Retrieval | Share of queries whose true person or relative appears in the top K |
| Pairwise **precision, recall, F1** | Each threshold | Plus the precision–recall curve |
| **Cluster quality** | After clustering | Entity-centric measures, because pairwise P/R can mislead for groups [B9] |
| **False-match rate** | Review and confirmation thresholds | Reported per slice |
| **False-non-match rate** | All thresholds | Per language, script, origin and source |
| **Calibration** | Scores | Reliability diagram and expected calibration error. A score of 0.8 should match about 80% observed |
| **Abstention** | Queries whose person isn't present | Share correctly answered "not found" or "insufficient evidence" |
| **Reviewer load** (proxy) | Review queue | Candidates per query above the review threshold |
| **Sensitive fields requested** (proxy) | Progressive disclosure | Fields opened per resolved synthetic case (week 9) |
| **Explanation coverage** | Every surfaced candidate | Share with a complete, valid path (observation → transforms → graph edges → weights) |

**Uncertainty:** 95% intervals by bootstrap **over families**, not over pairs.

## 6. Fairness slices

Every metric is reported for each of these slices, never only as a global average (§9.3):

- **origin / pack:** RW, BI, CD;
- **source type;**
- **record completeness:** number of non-empty fields;
- **age group:** child or adult;
- **sex:** synthetic, so lawful to measure;
- **error type** (from §2.3);
- **name frequency:** rare vs common tokens.

**Gap flag:** a slice's false-non-match rate more than **1.5×** the best slice's at the same threshold is flagged in the report and discussed.

## 7. Cost of errors and thresholds

The cost of each kind of error depends on the step (decided 26 Oct 2026; to confirm with the professor):

| Step | Worse error | Proposed ratio | How the threshold is set (on dev) |
| --- | --- | --- | --- |
| **Retrieval** (who enters the candidate list) | **Missed candidate** (the person is never seen by a human) | Missed : false = **10 : 1** | Highest threshold that keeps **recall@20 ≥ 0.95** |
| **Review priority** (order of the queue) | Balanced | 1 : 1 | Maximise F1; report the queue length |
| **Confirmation** (a reviewer may treat the pair as the same person) | **False match** (wrong person told, wrong child released, location exposed) | False : missed = **10 : 1** overall; **100 : 1 for minors** | Lowest threshold with **precision ≥ 0.99** (adults) and **≥ 0.999** (minors) on dev; abstain below it |

**Notes:**

- These targets are set **before** any results. If they turn out to be unreachable on synthetic data, the report says so; we don't lower the bar quietly.
- **A name-only score never reaches the confirmation step,** whatever its value (§5.6).
- Confirmation is still a **human decision**. The threshold only decides what the reviewer is shown as "strong evidence".

## 8. Procedure

0. **Weeks 4–5:** build the naming profiles (local), then delete the raw lists. Collect the real-pattern variants (sanctions-list aliases, 2014 spelling forms).
1. **Week 6:** write the generator (seeded, versioned). Run the fidelity test, and correct the generator if needed. Generate train, dev, test and holdout. Freeze test and holdout. Commit the generator and seeds; keep the generated data reproducible.
2. **Weeks 7–8:** fit and tune each option on train and dev only.
3. **Week 8:** run each option once on test. Report every metric × slice × track.
4. **Week 9:** run the temporal holdout once. Write the report, including failures, unreachable targets and differences from the §6 design scores.

## 9. Limits

- **The data is synthetic.** Results show whether the methods handle the error types we know about, not the ones we don't. The decisive benchmark needs real, governed error patterns (§9.1) and a partner.
- **Kirundi element frequencies are estimates** until a sourced list is found. Kinyarwanda uses the NESA exam lists, and the DRC uses CongoNames; both cover school-age candidates, so they under-represent older generations.
- **Realism is checked, not proven.** The fidelity test shows that names *look* real. Only phase 3, with a partner, shows that the errors *behave* like Dzaleka's.
- **The Burundi rule is disputed** (`SCOPE.md` §1), so results are reported across the range of *p*.
